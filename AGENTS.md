# pixbi_lineage — рабочая память

## Что это
Кастомная визуализация lineage данных (путь «источник → витрина → дашборд») для
дашбордов PIX BI. Реализация — один JS-файл на ECharts (`series.type: 'graph'`,
`layout: 'none'`, узлы позиционируются вручную по слоям), без сборщиков и пакетного
менеджера. Живёт локально в `D:\projects\pixbi_lineage`, публикуется в GitHub
(`origin` = https://github.com/Rail-Akhm/pixbi_lineage.git, ветка `main`).
Пользователь — автор дашбордов PIX BI (Rail-Akhm).

## 2026-10-19 — добавлена диаграмма Ганта
- **`gantt.js`** — отдельный кастомный визуал (не lineage): ECharts
  `series.type: 'custom'` + `coordinateSystem: 'cartesian2d'`. Слева 3 колонки
  (Номер ЗНИ | Исполнитель | Практика), справа календарь по дням; ячейка
  закрашена по `SUM(timeworked_h)`. `BLOCK_ID = 'vv86tlu5j3ljm7amqnvi2sj3nwqx0ax3'`
  (в локальном стенде переопределяется через `window.__GANTT_BLOCK_ID__`).
- Конфигурация блока: **одно вычисляемое поле** `gantt_key` =
  `dt|~|zni_number|~|full_name|~|practice|~|qrt`; мера `SUM(timeworked_h)`;
  серии пусто. Изначально планировались отдельные категории, но **прод-блок
  доказал, что getItemData этой версии PIX BI отдаёт только первую категорию**
  (в ответе 378 строк = число уникальных `dt`, а не 1373 комбинации из 5 полей).
  Поэтому склейка в одно поле — вынужденная мера платформы, а не дизайн.
  `gantt.js` также понимает современный формат `{values, columns}` и другие
  легаси-формы, если они появятся.
- Строки: группы ЗНИ с подстроками исполнителей, сворачиваются кликом по левой
  панели. В шапке (v2.5) только легенда часов, период и версия — селектор
  квартала, кнопки «Развернуть/Свернуть все» и счётчики убраны (делаются
  фильтрами и виджетами PIX BI). `?qrt=` на стенде по-прежнему работает через
  отладочный API `setQrt`.
- Грабли ECharts 5.4.3: в `renderItem` custom series **нет `params.data`** —
  только `params.dataIndex`; элементы берутся из `viewCells` / `viewDecor`.
- `debug_gantt.html` — стенд: мок `getItemData` из CSV, чекбоксы агрегации и
  тёмной темы. Тестовые URL-параметры: `?qrt=2025-II`, `?collapse=1`, `?dark=1`,
  `?raw=1`, `?tip=1`,
  `?format=rows|cats|cols|guess|transp|key|key2|singlecat|bad`. Запуск:
  `npx serve` → `/debug_gantt.html`.
- **Реальный PIX BI отдаёт легаси-формат `categories`** (как `lineage_v2.js`):
  `{name, series:[{value}], extra_hints}`. Поэтому `normalizeData` поддерживает
  все известные формы, а при отсутствии `columns` распознаёт поля по форме
  значений. Если данные не распознаны — блок сам печатает диагностику на экране
  (DevTools у пользователя заблокирован), включая готовую формулу `gantt_key`,
  если пришла только одна категория.
- Подробное описание — в `CLAUDE.md`, раздел «gantt.js — диаграмма Ганта».
- **`diag_categories.js`** — отдельный диагностический скрипт для проверки того,
  как платформа отдаёт несколько ОТДЕЛЬНЫХ категорий. Вставляется в блок вместо
  `gantt.js`, печатает отчёт на экране: дерево ответа `getItemData`, все поля
  объектов категорий, глубокий поиск массивов внутри ответа (где могли бы быть
  колонки), проверку 5 способов чтения, вызовы `getItemData` с другими
  аргументами и другие функции API. Первой строкой — короткий ИТОГ. Кнопка
  «Перепроверить» + автоповтор через 2,5 с. `window.__DIAG_BLOCK_ID__`
  переопределяет `BLOCK_ID`.
- **Устройство API (проверено на прод-блоке 19.10.2026):**
  `getItemData = (id) => window.itemsData[id] || {}`. С пустым аргументом,
  DOM-элементом и `{id}` возвращает `{}`. При 5 категориях в ответе 69 строк
  (уникальные `zni_number` — первая категория), не 1373 комбинации: платформа
  группирует только по ПЕРВОЙ категории, и её порядок в блоке определяет, какое
  поле придёт. У категорий только `name` / `series` / `extra_hints`,
  `metadata` и `customValues` — `undefined`. При этом в `data_configs` блока
  сохранены 4 категории, а датасет `v_serv_jira_zni_gant` содержит 22 поля —
  конфигурация полная, но платформа отдаёт только первое измерение. Поэтому
  ключ через `|~|` — единственный способ передать все измерения. Для даты в
  `concat` нужен строковый тип: `toString(dt)` / `cast(dt as varchar)`.
- **`diag_gantt.js`** (19.10.2026) — короткая диагностика именно данных Ганта:
  вставляется в блок вместо `gantt.js`, печатает на экране число строк,
  разделитель и части `gantt_key`, счётчики разбора (принято / без даты / без
  ЗНИ / без часов), уникальные ЗНИ / исполнители / практики / кварталы, период,
  сумму часов, первые разобранные строки и сверку с `EXPECTED`. Итог —
  однозначный вердикт; при одной категории без `|~|` показывает готовую формулу
  `gantt_key`. `BLOCK_ID` переопределяется через `window.__DIAG_GANTT_BLOCK_ID__`.

  ко записей за день, берётся состояние на конец дня — значение с максимальным
  `running_sum_timeworked_h`; для свёрнутой группы — сумма разниц по исполни-
  телям. Поле читается либо из колонки `kcp_jira_time_diff_h` (табличный
  формат), либо из необязательной части ключа `|~|trz_diff=<число>`

  Проверено headless Chrome на CSV: `?format=csvkey&tip=diff` → `+154,3 ч`,
  `?format=csvkey&tip=neg` → `−3,98 ч` (красное), тёмная тема,
  `?collapse=1` (сумма по группе), `?format=keydesc`, `?format=allcats`.
- **Стенд разницы ТРЗ:** `?tip=diff` / `?tip=neg` — скроллит к первой ячейке

  разницу на конец дня. `gantt_multi.js` не менялся (разработка на паузе).

## Ключевые факты и грабли
- **Один блок = один `lineage_key`.** v2 ждёт ОДНО вычисляемое поле-категорию
  `lineage_key`, меру `COUNT(1)` (без меры PIX BI вернёт 0 строк) и ПУСТЫЕ серии.
- Формат: `Название::значение::инфо` на сегмент, сегменты через `||`
  (`LAYER_SEP`), внутри сегмента `FIELD_SEP = '::'`. Слой определяется **позицией**
  сегмента, а не названием — одинаковые названия на разных слоях допустимы.
  Число слоёв = число сегментов; добавлять/убирать слой нужно в SQL-формуле, код править
  не надо. Практический потолок — 20 слоёв (длина `COLOR_PALETTE`).
- Найденные в коде константы: `BLOCK_ID` (строка в начале `lineage_v2.js`, тот же ID и
  в `lineage.js` как `const id`, и в `debug.html` — при пересоздании блока править все
  три места), `NODE_W = 160`, `NODE_H = 30`, `V_GAP = 24`, `PAD = 80`,
  `MIN_LAYER_GAP = 80` (в коде помечено `← ПРАВИТЬ ЗДЕСЬ`), `COMFORTABLE_GAP = NODE_W + 80`,
  `EMPTY_LAYER_GAP = 30`.
- **Главная грабля — авто-fit ECharts.** При `layout:'none'` ECharts сам вписывает весь
  граф в контейнер и схлопывает узлы в кучу; декларативные `zoom`/`center` это не лечат.
  Рабочее решение: canvas (`innerEl`) физически равен размеру графа
  (`logicalW × logicalH`), вложен в `scrollEl` с `overflow: hidden`; зум/панорама —
  только через `roam` (нативный скролл перехватывает мышь и ломает `draggable`).
  После рендера `centerScroll()` центрирует вид с повторами (PIX BI грузится асинхронно,
  `clientWidth/Height` могут быть 0). Предыдущие попытки (`CSS transform:scale`,
  фиксированный `NODE_VERTICAL_GAP`, явный `initLayout` zoom/center) в git откачены —
  см. коммиты `5cce3a2`, `3dd8b81`, `24d8551`.
- **`replaceMerge` сбрасывает состояние.** Подсветка/reset должны брать живые значения
  через `currentView()` (zoom/center) и `getCurrentPositions()` (x/y после драга), иначе
  ручной зум и позиции узлов откатываются при hover/click/reset.
- Рёбра строятся внутри строки: сегмент i → ближайший непустой сегмент справа; пустые
  сегменты пропускаются, хвостовой `||` игнорируется. Дедупликация рёбер — `linkSet`
  с ключом `src>>tgt`. ID узла = `${layerIndex}::${value}`.
- Тема берётся адаптивно из `window.themeConfigs`; отслеживание — `MutationObserver` +
  `postMessage` с типом `THEME_CHANGED`. Цвета/тему НЕ хардкодить.
- Нет `package.json`, `requirements.txt`, `pyproject.toml`, docker/Makefile — приложение
  без сборки. ECharts в проде предоставляет хост PIX BI; версия 5.4.3 зафиксирована только
  в `debug.html`.
- Датасет v1: в `CLAUDE.md` упомянут файл
  `edw_prj_brddwh_v_serv_dashboard_linage_prod_202606031303.csv` (~15 634 строк, разделитель `;`),
  но фактически в `data/` лежат `dataset.csv` (11,9 МБ, 08.06.2026) и `dataset.xlsx`
  (2,3 МБ). Совпадение имени не проверено.
- В `data/` также 10 скриншотов `image1..image10.png` (эталонные виды графа) и
  `памятка_экономия_токенов.txt` — руководство по плагину Claude Code cost-mode; к коду
  проекта отношения не имеет.
- Секретов в проекте нет: в `.claude/settings.local.json` только разрешения

## Как запускать и проверять
Локальная отладка (из README):
```
npx serve
# открыть http://localhost:3000/debug.html
```
В `debug.html`: выбрать CSV-файл (чекбокс `limit` ограничивает вывод первыми 500 строками),
нажать «Запустить lineage_v2.js» — скрипт подгрузится тегом `<script>`.
Через `file://` не работать (об этом прямо предупреждает `onerror` в `debug.html`).
ID DOM-контейнера в `debug.html` должен совпадать с `BLOCK_ID` в `lineage_v2.js`.

Выкладка в прод — вручную: скопировать содержимое `lineage_v2.js` в кастомную
визуализацию блока PIX BI, предварительно сверив `BLOCK_ID` с ID блока.

Проверка результата — визуально: слои слева направо по числу сегментов `lineage_key`,
узлы `roundRect` натурального размера 160×30, легенда зафиксирована сверху, drag узлов
и подсветка пути не сбрасываются при hover/click/reset.
