# PIXBI Lineage Visualizer

Интерактивная визуализация lineage данных для дашбордов PIXBI.
Реализация: кастомные визуализации PIX BI на **ECharts** — граф lineage
(`series.type: 'graph'`, `layout: 'none'` — узлы позиционируются вручную по слоям)
и диаграмма Ганта (`series.type: 'custom'`, `cartesian2d`).

---

## 📁 Структура проекта

```
pixbi_lineage/
├── lineage.js        # Кастомная визуализация PIX BI v1 (legacy, одна категория, 5 слоёв)
├── lineage_v2.js     # Кастомная визуализация PIX BI v2 (несколько блоков, динамические слои)
├── gantt.js          # Диаграмма Ганта по трудозатратам (custom series + cartesian2d)

```

# gantt.js — диаграмма Ганта

Классическая диаграмма Ганта по трудозатратам: слева три колонки
**Номер ЗНИ | Исполнитель | Практика**, справа — календарь по дням.
Ячейка дня закрашена по `SUM(timeworked_h)`.

Реализация — ECharts `series.type: 'custom'` + `coordinateSystem: 'cartesian2d'`
(не `graph`), `dataZoom` для времени и строк, rich-text для левой панели.

## Конфигурация блока PIX BI

| Параметр | Значение |
|----------|----------|
| Категории | **одно вычисляемое поле `gantt_key`** (см. формулу ниже) |
| Меры | `SUM(timeworked_h)` — обязательно |
| Серии | пусто |
| `BLOCK_ID` | `vv86tlu5j3ljm7amqnvi2sj3nwqx0ax3` (в начале `gantt.js`) |

**Важно (проверено на прод-блоке 19.10.2026):** `getItemData` этой версии
PIX BI отдаёт **только первую категорию** блока. Если в «Категориях» пять полей,
в ответе всё равно приходят только значения `dt` (378 строк = число уникальных
дат, а не 1373 комбинации). Поэтому пять полей склеиваются в одно вычисляемое
поле `gantt_key` через разделитель `|~|`:

```sql
concat(
  coalesce(toString(dt), ''), '|~|',
  coalesce(zni_number, ''),   '|~|',
  coalesce(full_name, ''),    '|~|',
  coalesce(practice, ''),     '|~|',
  coalesce(qrt, ''),          '|~|',
  'zni_name=', coalesce(epic_summary, ''), '|~|',
  'trz_diff=', coalesce(toString(kcp_jira_time_diff_h), '')
)
```

Шестая часть — **описание ЗНИ с явной меткой** `zni_name=`. Метка снимает
неоднозначность: свободный текст («[ВНИ] Доработка витрины …»), содержит пробелы,
запятые и может быть длинным, поэтому распознавать его по форме нельзя. Части
`метка=значение` понимаются для полей `dt`, `zni`, `person`, `practice`, `qrt`,
`zniInfo` (синонимы: `zni_name`, `zni_desc`, `zni_info`, `zni_description`,
`описание`, `название`, `summary`, `epic_summary`), `trzDiff` (синонимы:
`trz_diff`, `kcp_jira_time_diff_h`, `разница_трз`, `diff_h`, `diff`) и
обрабатываются **до** распознавания по форме, независимо от позиции. Без шестой
части ключ остаётся рабочим — просто тултип по номеру ЗНИ будет без описания.

Седьмая часть — **разница ТРЗ** (оценка из предварительных ДО минус факт из Jira),
необязательная: без неё в подсказке ячейки просто нет нижнего блока. Число
показывается **только при наведении** на ячейку дня, ниже фактических часов,
с цветом по градиенту (см. «Отображение»). В режиме «Все категории» это же
значение читается из колонки `kcp_jira_time_diff_h`.

Порядок частей в формуле выше — рекомендуемый, но **не обязательный**:
`gantt.js` распознаёт части по форме значений (дата, квартал `2026-I`, числовой
ЗНИ, «Практика…», ФИО из 2+ слов), поэтому работает и ключ из 2 полей
(категория + дата), и из любого другого числа 2..N. При 2 полях группа
показывается одной строкой без подстрок исполнителей.
Ответ API выглядит так:

```js
{ categories: [
  { name: '2025-01-29|~|5500046555|~|Дунаев Алексей Игоревич|~|Практика…|~|2026-I|~|zni_name=Описание ЗНИ|~|trz_diff=154.3',
    series: [{ name: "SUM('v_serv_jira_zni_gant'[timeworked_h])", value: '2' }] }
] }
```

`gantt.js` разбирает `categories[i].name` по `KEY_SEP = '|~|'`, а часы берёт из
`categories[i].series[0].value`. Сырые строки агрегируются в JS по
`(zni_number, full_name, dt)`.

Дополнительно поддержаны и другие форматы `getItemData`: современный
`{ values, columns }`, `categories` как массив записей, `{name:[значения],
value: мера}`, массив кортежей, объект массивов, массив колонок и
транспонированный массив. Если `columns` нет, поля распознаются по форме
значений (дата, квартал `2026-I`, числовой ЗНИ, «Практика…», ФИО из 2+ слов).
В стенде: `?format=rows|cats|cols|guess|transp|key|key2|csvkey|keydesc|allcats|singlecat|bad`
(`key2` — ключ из 2 полей: ЗНИ + дата; `csvkey` — реальное вычисляемое поле
`gantt_key` из CSV, сгруппированное как в PIX BI; `keydesc` — тот же ключ
с шестой частью `zni_name=<epic_summary>`; `allcats` — режим данных
**«Все категории»**: `{values, columns}`, мера названа выражением
`SUM('v_serv_jira_zni_gant'[timeworked_h])`, описание и разница ТРЗ —
отдельными колонками). `csvkey` и `keydesc` добавляют к ключу
`|~|trz_diff=<kcp_jira_time_diff_h>`, если значение в строке есть.
Параметр `?diag=1` запускает вместо `gantt.js` диагностический `diag_gantt.js`.

### Несколько категорий: режим данных «Все категории»

Документация PIX BI («Примеры ECharts», раздел Nested Pies / Js-таблица)
показывает два режима данных:

- **«Дриллдаун»** — платформа отдаёт **одну текущую категорию** (уровень
  детализации) и меры/серии. Именно поэтому при пяти полях в «Категориях»
  `getItemData` возвращал только первую — и появился `gantt_key`.
- **«Все категории»** — возвращается плоская таблица всех полей:
  `columns: [{name, alias}, ...]`, `values: [{ <имя колонки>: {value}, ... }]`.
  Это штатный способ получить несколько отдельных категорий.

Для Ганта без склейки: в блоке выбрать режим «Все категории», на полку
«Категории» положить `dt`, `zni_number`, `full_name`, `practice`, `qrt`
(и `epic_summary`, если нужно описание), на «Меры» — `SUM(timeworked_h)`,
«Серии» — пусто. `gantt.js` читает такую таблицу через `normalizeData` →
`handleRow` → `readRecord` по именам колонок/алиасов из `FIELDS`; проверено
на стенде (`?format=allcats`): 69 ЗНИ, 21 исполнитель, 3601.5 ч, описание
в подсказке работает. `gantt_key` в этом режиме не нужен. `diag_gantt.js`
пока разбирает только `categories` и в режиме «Все категории» покажет
«categories: нет» — его нужно дополнить чтением `values + columns`.

### gantt_multi.js — отдельный вариант для нескольких категорий

Основной рабочий вариант (`gantt.js`, режим «Дриллдаун» + `gantt_key`)
**остаётся без изменений**. Для блоков, где данные приходят отдельными
категориями, сделан второй файл — `gantt_multi.js`. Это самостоятельный
форк `gantt.js`: тот же визуал, но заточен под режим данных
**«Все категории»** (`{values, columns}`), где `gantt_key` не нужен.

| Параметр блока | `gantt.js` (основной) | `gantt_multi.js` |
|----------------|-----------------------|------------------|
| Режим данных PIX BI | «Дриллдаун» | **«Все категории»** |
| Категории | одно поле `gantt_key` | `dt`, `zni_number`, `full_name`, `practice`, `qrt` (+ `epic_summary`) |
| Меры | `SUM(timeworked_h)` | `SUM(timeworked_h)` |
| Серии | пусто | пусто |
| Версия в шапке | `v2.7` | `v1.0-multi` |

Отличия от `gantt.js`:

- `BLOCK_ID` берётся из `window.__GANTT_MULTI_BLOCK_ID__`, затем из
  `window.__GANTT_BLOCK_ID__`, иначе — ID блока Ганта по умолчанию
  (`vv86tlu5j3ljm7amqnvi2sj3nwqx0ax3`).
- `GANTT_VERSION = '1.0-multi'`, в тултипе версии написано
  «много категорий, режим «Все категории»» — по шапке видно, какой файл
  загружен.
- `readHours(rec)`: часы берутся из точного поля `FIELDS.hours`, а если его
  нет — из любой колонки, чьё имя похоже на `timeworked` / `hours` / `час`
  (мера в «Все категории» часто называется выражением
  `SUM('v_serv_jira_zni_gant'[timeworked_h])`).
- Экран пустых данных и финальная подсказка ведут в режим «Все категории»:
  перечислить поля на «Категориях», меру — на «Мерах», «Серии» — пусто.
- Разбор `gantt_key` и всех легаси-форматов сохранён как запасной путь
  (тот же `normalizeData`), поэтому `gantt_multi.js` не падает и на старых
  данных.

Всё остальное (строки, кварталы, свёртка групп, крутилка, зум, описание ЗНИ,
цвета практик) идентично `gantt.js`. Стенд:
`debug_gantt.html?multi=1&format=allcats` — запускает `gantt_multi.js`
на моке «Все категории». Проверено headless Chrome: `v1.0-multi`,
69 ЗНИ · 21 исполнитель · 3601,5 ч, подсказка описания ЗНИ работает.

Если данных распознать не удалось, блок рисует экран диагностики
(`describeData`) с ключами ответа, списком `columns`, первыми строками и
счётчиками разбора — DevTools для этого не нужен. Если пришла только одна
категория без `|~|`, экран сам показывает готовую формулу `gantt_key`.

## Отображение

- **Строки:** группы по `zni_number`; под каждой — исполнители. Клик по строке
  ЗНИ в левой панели сворачивает/разворачивает группу. В свёрнутой группе
  показывается сумма по всем исполнителям за день.
- **Шапка (v2.5):** только градиентная легенда часов, период данных и версия
  скрипта. Встроенных фильтров и счётчиков нет — селектор квартала, кнопки
  «Развернуть все» / «Свернуть все» и статистика (`N ЗНИ · M исполнителей`)
  убраны: фильтры и счётчики настраиваются средствами PIX BI.
- **Ось X:** все дни диапазона — от минимальной до максимальной даты данных.
  Квартальный диапазон остался только в отладочном API (`setQrt`), в проде
  диапазон задаётся фильтрами PIX BI.
- **Цвет дня:** глобальная шкала `0 → max(hours)` (5 стопов, отдельные наборы для
  светлой/тёмной темы). Максимум учитывает и агрегаты свёрнутых групп, поэтому
  шкала стабильна между фильтрами. Значения растягиваются по гамме
  `HEAT_GAMMA = 0.6` (`t = (hours / max)^0.6`): ячейки с малым числом часов
  получают заметно более насыщенный цвет и не сливаются со светло-синим фоном
  дашборда. Легенда-градиент сэмплируется в 12 точках, чтобы совпадать с
  нелинейной шкалой.
  - светлая тема: `#7ab6ea → #5aa9e6 → #2f84d6 → #175bb5 → #0a2f63`
  - тёмная тема: `#12527d → #0c6ba8 → #1195dc → #38bdf8 → #bae6fd`
- **Часы в ячейке (v2.6):** внутри закрашенного дня пишется `SUM(timeworked_h)`
  (`fmtCellHours`: компактно, без хвостовых нулей, запятая — `0,28`, `8,17`, `10`).
  Цвет подписи подбирается по яркости заливки (`labelColorFor`, WCAG-яркость):
  тёмный `#0f172a` на светлых ячейках, белый — на тёмно-синих.
  Подписи включаются только при достаточном зуме: ширина одного дня
  `s[0] >= CELL_LABEL_MIN_W` (24 px) и высота ячейки ≥ 12 px. На обзоре периода
  (день 2–10 px) цифр нет — остаются только цвета.
- **Разница ТРЗ в подсказке (v2.7):** значение `kcp_jira_time_diff_h` (или часть
  ключа `trz_diff=…`) показывается **только при наведении** на ячейку — ниже
  фактических часов, отдельным блоком с подписью «Разница ТРЗ из предварительных
  ДО и фактических ТРЗ из Jira». Число — со знаком и запятой (`+154,3 ч`,
  `−3,98 ч`), цвет `trzDiffColor`: жёлтый на нуле, зелёный на максимуме,
  красный на минимуме (`v < 0`); диапазон — `model.minDiff` / `model.maxDiff`
  по всем ячейкам, поэтому цвет стабилен между фильтрами. Если в одном дне
  несколько записей, берётся состояние на конец дня — значение с максимальным
  `running_sum_timeworked_h`; в свёрнутой группе — сумма разниц по исполнителям.
  Если значения в данных нет, нижний блок подсказки не выводится. На самих
  квадратиках и в зуме по-прежнему только часы.
- **Цвет практик:** `PRACTICE_COLORS` (18 различимых цветов, запас на будущее;
  сейчас в данных 2 практики) по алфавиту названий практик.
- **Подписи X:** при обзоре всего периода — только месяцы; при зуме ≤ 140 дней
  добавляются числа `5/10/15/20/25`. Месяц подписывается 1-м числом (у января —
  с годом). Это обходит `hideOverlap`, который иначе выбрасывает месяцы.
- **Декор:** полосы групп, зебра исполнителей, выходные (сб+вс объединены),
  вертикальные линии границ месяцев.
- **Вертикальная крутилка справа:** кастомный HTML-элемент поверх canvas
  (`.pg-vbar` / `.pg-vthumb`), высота дорожки = область строк
  (`GRID_TOP`..`GRID_BOTTOM`). Ползунок пропорционален числу видимых строк,
  перетаскивается (`pointerdown` + `setPointerCapture`), клик по треку —
  прыжок к позиции, колесо над полосой — построчный скролл. При нехватке строк
  скрывается. Позиция синхронизирована с `state.yStart` через `applyYWindow()`.

## Взаимодействие

| Действие | Результат |
|----------|-----------|
| Клик по строке ЗНИ в левой панели | Свернуть / развернуть группу |
| Колесо мыши | Вертикальный скролл строк |
| Вертикальная полоса справа | Прокрутка списка ЗНИ: перетаскивание ползунка или клик по треку |
| Ctrl/Cmd + колесо | Зум по времени вокруг центра |
| Нижний слайдер | Панорама / зум по времени |
| Hover по ячейке | Тултип: ЗНИ, исполнитель (или «N исполнителей» для агрегата), практика, дата, часы; ниже — «Разница ТРЗ из предварительных ДО и фактических ТРЗ из Jira» и цветное число, если разница есть в данных |
| Hover по номеру ЗНИ в левой панели | Всплывающая подсказка `.pg-ztip`: «ЗНИ <номер>» + описание из `zni_name=…` (если описания нет — подсказка не показывается). Тултип ячеек дня при этом не меняется |

## Грабли

- **ECharts 5.4.3:** в `renderItem` custom series **не передаётся `params.data`** —
  только `params.dataIndex`. Элементы берутся из `viewCells[dataIndex]` /
  `viewDecor[dataIndex]`, а не из `params.data`.
- **`renderItem` нельзя возвращать массив элементов.** Проверено на 5.4.3:
  `return [rect, text]` (и даже `[rect]`) падает с пустым `Error` внутри
  `customSeries._add`, `setOption` при этом оставляет **старые** элементы от
  предыдущего прохода (график выглядит рабочим, но геометрия не обновляется —
  именно так «пропадали» подписи часов). Рабочий вариант — группа:
  `return { type: 'group', children: [rect, text] }`.
- `dataZoom`: `filterMode: 'none'`, id `dzX` / `dzY` / `dzXSlider`; вертикальное
  окно строк применяется через `dispatchAction` (`startValue` / `endValue`).
- Левая панель — rich-text в `yAxis.axisLabel` (`inverse: true`, `margin:
  LEFT_W - 16`), а не отдельный HTML; ширина `LEFT_W = 500`.
- Тема адаптивная (`window.themeConfigs`), отслеживание — `MutationObserver` +
  `postMessage({ type: 'THEME_CHANGED' })`.
- **`<style id="pixbi-gantt-style">` перезаписывается при каждом запуске.**
  Дашборд PIX BI — SPA: после повторного рендера визуала старый тег остаётся
  в `<head>`, и если вставлять стили только при его отсутствии, новые классы
  (например, `.pg-vbar`) не применяются. Поэтому `textContent` обновляется
  всегда.
- В шапке справа отображается версия скрипта (`v2.7`) — по ней видно, что
  PIX BI подхватил новую версию, а не закешировал старую.
- **Подсказка описания ЗНИ — отдельный HTML-элемент `.pg-ztip`**, а не тултип
  ECharts: `mousemove` на `chart.getZr()` проверяет `e.offsetX <= COL_ZNI + 12`,
  строка определяется через `convertFromPixel({yAxisIndex:0}, e.offsetY)`.
  Скрывается на `globalout` и в начале `applyYWindow()`. Цвета берутся из темы,
  позиция прижимается к краям `chartEl`.

## Локальная отладка

`debug_gantt.html` подменяет `getItemData` и читает CSV (`;`), автоматически
загружает `data/serv_jira_zni_gant_202610201349.csv` (2345 строк, 1810
уникальных `gantt_key` без разницы ТРЗ и 1884 с частью `trz_diff=…`; разница
заполнена в 1073 строках). Есть чекбоксы «агрегировать как PIX BI» и «тёмная
тема», кнопка «Запустить gantt.js».

Тестовые URL-параметры: `?qrt=2025-II`, `?collapse=1`, `?dark=1`, `?raw=1`,
`?tip=1` (показать тултип на самой «горячей» видимой ячейке),
`?tip=diff` (прокрутить к первой ячейке с разницей ТРЗ и показать тултип),

```js
getItemData = (id) => window.itemsData[id] || {};
```

# lineage_v2.js (актуальная версия)

## Архитектура: один блок, склейка пути через `||`

v2 использует **один блок PIX BI** с **одним вычисляемым полем** `lineage_key`,
в котором весь путь склеен через разделитель слоёв `||`. Каждый сегмент между
`||` = один слой графа (по позиции). В отличие от v1, число слоёв **динамическое**
(определяется числом сегментов), а не захардкожено.

```
lineage_key (одно поле) ──► lineage_v2.js ──► ECharts Graph
  "Схема::v1::инфо || Таблица::v2::инфо || Витрина::v3::инфо || Дашборд::v4::инфо"
       слой 0            слой 1           слой 2            слой 3
```

### Конфигурация в PIX BI

**Блок** (где `lineage_v2.js`):
- **Категории:** ОДНО вычисляемое поле `lineage_key` (формат ниже)
- **Меры:** `COUNT(1)` — обязательно, иначе 0 строк
- **Серии:** пусто
- `BLOCK_ID` в `lineage_v2.js` = ID этого блока (он же DOM-элемент для рендера)

### Формат данных (`lineage_key`)

Каждая строка `categories[i].name` = одна цепочка пути:

```
Название::значение::инфо || Название::значение::инфо || ...
```

- **Разделитель слоёв:** `||` (`LAYER_SEP`). Каждый сегмент = слой по позиции.
- **Внутри сегмента:** `Название::значение::инфо` (`FIELD_SEP` = `::`).

| Часть | Назначение |
|-------|------------|
| `Название` | Метка слоя (легенда). Слой определяется ПОЗИЦИЕЙ, не названием — одинаковые названия на разных слоях допустимы. |
| `значение` | Имя узла (внутри узла и в тултипе). |
| `инфо` | Доп. информация (синим в тултипе). Может быть пустым. |

Связи строятся **внутри строки**: сегмент i → следующий непустой сегмент i+1.
Отдельный «ключ» не нужен. Пустые сегменты (значение `''`) пропускаются — ребро
идёт к ближайшему непустому слою справа. Завершающий `||` (пустой хвостовой слой)
игнорируется.

**Пример SQL (PIX BI вычисляемое поле):**
```sql
concat(
  'Схема в GreenPlum',  '::', coalesce(table_schema,''), '::', concat('Домен СИДа: ', coalesce(sid_domen,'')), '||',
  'Таблицы в GreenPlum','::', coalesce(table_name,''),   '::', concat('Домен СИДа: ', coalesce(sid_domen,'')), '||',
  'Витрины в GreenPlum','::', coalesce(view_schema,''),  '::', concat('Домен СПДа: ', coalesce(spd_domen,'')), '||',
  'Витрины в GreenPlum','::', coalesce(view_name,''),    '::', concat('Домен СПДа: ', coalesce(spd_domen,''))
) as lineage_key
```

### `BLOCK_ID`

В начале `lineage_v2.js`:

```js
const BLOCK_ID = 'id_блока';   // ID блока, он же DOM-элемент для рендера
```

**Число и порядок слоёв** задаётся числом и порядком сегментов в `lineage_key`
(макс. 20 — по размеру палитры). Чтобы добавить/убрать слой — правится SQL-формула,
код менять не нужно.

## 🎨 Дизайн и поведение (v2)

### Узлы
- `symbol: 'roundRect'`, фиксированный размер `[NODE_W, NODE_H]`
  (`NODE_W = 160`, `NODE_H = 30`) — узлы НЕ сжимаются
- Цвет — `COLOR_PALETTE[layerIndex]`, обводка `#fff`, подпись внутри
- Слои по горизонтали: динамический зазор `dynGap`, подбирается под ширину блока
  - `MIN_LAYER_GAP = 80` (править вручную, строка с комментарием `← ПРАВИТЬ ЗДЕСЬ`)
  - `COMFORTABLE_GAP = NODE_W + 80 = 240` — когда хватает места
  - Пустые слои (без узлов): `EMPTY_LAYER_GAP = 30` — чтобы соседние непустые слои не разъезжались
  - Если слои не влезают даже с `MIN_LAYER_GAP` → горизонтальный скролл
- Узлы внутри слоя — вертикально, шаг `NODE_H + V_GAP` (`V_GAP = 24`),
  сортировка по имени

### Размер canvas и обход авто-fit (важно)
ECharts с `layout:'none'` по умолчанию **авто-вписывает** (fit) весь граф в
размер контейнера — при множестве узлов это схлопывает их в кучу. Декларативный
`zoom`/`center` это не лечит (fit перебивает их).

Решение: **canvas делается физически равным размеру графа**.
- Узлы сдвигаются в положительные координаты от `(PAD, PAD)` (`PAD = 80`).
- Вычисляются `logicalW × logicalH` по bbox узлов + поля.
- Внутри `scrollEl` (прокручиваемый контейнер) создаётся `innerEl` размером
  `logicalW × logicalH`, и ECharts рендерит **на нём**. Авто-fit становится
  тождественным (вписывать граф в canvas его же размера нечего) → масштаб 1,
  узлы натуральные, зазоры держатся.
- `scrollEl.style.overflow = 'hidden'` — панорамирование/зум только через
  ECharts `roam` (иначе scrollEl перехватывает мышь и ломает draggable).
- После рендера `centerScroll()` ставит середину графа по центру видимой области
  (с повтором — PIX BI грузится асинхронно, `clientWidth/Height` могут быть 0).

### Структура DOM внутри блока
```
el (flex column, overflow:hidden)
├── headerEl (flex-shrink:0) — фиксированная HTML-легенда (не скроллится)
└── scrollEl (flex:1, overflow:hidden) — область с графом (pan/zoom через roam)
    └── innerEl (logicalW × logicalH) — ECharts canvas
```
Легенда вынесена из ECharts в отдельный HTML (цветные квадраты + названия слоёв)
и зафиксирована вверху — больше не уезжает вместе с графом при скролле.

### Рёбра
- Направленные (`edgeSymbol: ['none', 'arrow']`), `curveness: 0.3`
- По умолчанию `#94a3b8`, при выделении пути — `#60a5fa`

### Взаимодействие
- **Hover / клик** → подсветка полного пути: узел увеличивается, предки —
  синяя обводка, потомки — зелёная, рёбра пути жирные/синие, остальное гаснет.
  Клик закрепляет (`lockedNodeId`), повторный клик / клик по пустому месту — снимает.
- **Двойной клик** → сброс.
- **Тултип**: `_fullName`, `_info` (синим), название слоя + индекс, `refCount`.
- `roam` (zoom/pan) + `draggable` (перетаскивание узлов), `scaleLimit` 0.3..4.
- Панорамирование/зум мышью через roam (scrollEl с overflow:hidden,
  нативный скролл не используется). Дефолтный фокус — центр графа (`centerScroll`).
- `currentView()` читает текущий zoom/center из модели ECharts, чтобы подсветка
  пути (`replaceMerge`) не сбрасывала ручной зум/панораму к стартовому виду.
- `getCurrentPositions()` — читает живые x/y узлов из модели ECharts. Подмешивается
  в highlight/reset, чтобы replaceMerge не сбрасывал позиции, изменённые драгом.
- **Перетаскивание узлов**: после драга позиция сохраняется в модели ECharts.
  `buildHighlightedOption` / `buildResetOption` используют `getCurrentPositions()`,
  а не статичный `nodeData`, поэтому драг не сбрасывается при hover/click/reset.

### Тема
- Адаптивная из `window.themeConfigs`.
- Отслеживание: `MutationObserver` + `postMessage` (`THEME_CHANGED`).
- При смене темы перерисовывается и HTML-легенда (цвет текста).

### Диагностика
- Если нет данных — дамп на canvas с подсказками.

| Граф | ECharts `series.type: 'graph'` |
| Layout | `layout: 'none'` — динамическое позиционирование (`MIN_LAYER_GAP`, `EMPTY_LAYER_GAP`, `dynGap`) |

| Взаимодействие | `roam`/`draggable` + кастомные `click`/`dblclick` |
| Данные | `getItemData(id)` → `categories[i].name` |
| Тема | `window.themeConfigs` |

## 📐 Конвенции

- ECharts, `series.type: 'graph'`, `layout: 'none'` (lineage) /
  `series.type: 'custom'`, `cartesian2d` (Ганта)
- Один файл `.js` на версию, без сборщиков
- Язык интерфейса: русский
- Тема адаптивная (PIX BI), **не** хардкод
- **Новые дашборды lineage — `lineage_v2.js`**. `lineage.js` — для старых блоков.
- Диаграмма Ганта — `gantt.js` (режим «Дриллдаун» + `gantt_key`, основной
  вариант) или `gantt_multi.js` (режим «Все категории», отдельные колонки).
  Это не lineage-граф, отдельный тип блока.
- `BLOCK_IDS` / `const id` / `BLOCK_ID` — обновлять при пересоздании блоков
