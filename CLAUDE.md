# PIXBI Lineage Visualizer

Интерактивная визуализация lineage данных для дашбордов PIXBI.
Реализация: кастомные визуализации PIX BI на **ECharts** — граф lineage
(`series.type: 'graph'`, `layout: 'none'` — узлы позиционируются вручную по слоям)
и диаграмма Ганта (`series.type: 'custom'`, `cartesian2d`).

---

## 📁 Структура проекта

```
pixbi_lineage/
├── lineage.js        # Кастомная визуализация PIX BI v1 (legacy, одна категория, 5 слоёв)

├── debug_gantt.html  # Локальная отладка gantt.js: мок getItemData + CSV
```

# gantt.js — диаграмма Ганта

Классическая диаграмма Ганта по трудозатратам: слева три колонки
**Номер ЗНИ | Исполнитель | Практика**, справа — календарь по дням.
Ячейка дня закрашена по `SUM(timeworked_h)`.

Реализация — ECharts `series.type: 'custom'` + `coordinateSystem: 'cartesian2d'`
(не `graph`), `dataZoom` для времени и строк, rich-text для левой панели.

## Конфигурация блока PIX BI

| Параметр | Значение |
|----------|----------|
| Категории | **одно вычисляемое поле `gantt_key`** (см. формулу ниже) |
| Меры | `SUM(timeworked_h)` — обязательно |
| Серии | пусто |
| `BLOCK_ID` | `vv86tlu5j3ljm7amqnvi2sj3nwqx0ax3` (в начале `gantt.js`) |

**Важно (проверено на прод-блоке 19.10.2026):** `getItemData` этой версии
PIX BI отдаёт **только первую категорию** блока. Если в «Категориях» пять полей,
в ответе всё равно приходят только значения `dt` (378 строк = число уникальных
дат, а не 1373 комбинации). Поэтому пять полей склеиваются в одно вычисляемое
поле `gantt_key` через разделитель `|~|`:

```sql
concat(
  coalesce(toString(dt), ''), '|~|',
  coalesce(zni_number, ''),   '|~|',
  coalesce(full_name, ''),    '|~|',
  coalesce(practice, ''),     '|~|',
  coalesce(qrt, '')
)
```

Порядок частей в формуле выше — рекомендуемый, но **не обязательный**:
`gantt.js` распознаёт части по форме значений (дата, квартал `2026-I`, числовой
ЗНИ, «Практика…», ФИО из 2+ слов), поэтому работает и ключ из 2 полей
(категория + дата), и из любого другого числа 2..N. При 2 полях группа
показывается одной строкой без подстрок исполнителей.
Ответ API выглядит так:

```js
{ categories: [
  { name: '2025-01-29|~|5500046555|~|Дунаев Алексей Игоревич|~|Практика…|~|2026-I',
    series: [{ name: "SUM('v_serv_jira_zni_gant'[timeworked_h])", value: '2' }] }
] }
```

`gantt.js` разбирает `categories[i].name` по `KEY_SEP = '|~|'`, а часы берёт из
`categories[i].series[0].value`. Сырые строки агрегируются в JS по
`(zni_number, full_name, dt)`.

Дополнительно поддержаны и другие форматы `getItemData`: современный
`{ values, columns }`, `categories` как массив записей, `{name:[значения],
value: мера}`, массив кортежей, объект массивов, массив колонок и
транспонированный массив. Если `columns` нет, поля распознаются по форме
значений (дата, квартал `2026-I`, числовой ЗНИ, «Практика…», ФИО из 2+ слов).
В стенде: `?format=rows|cats|cols|guess|transp|key|key2|csvkey|singlecat|bad`
(`key2` — ключ из 2 полей: ЗНИ + дата; `csvkey` — реальное вычисляемое поле
`gantt_key` из CSV, сгруппированное как в PIX BI). Параметр `?diag=1` запускает
вместо `gantt.js` диагностический `diag_gantt.js`.

Если данных распознать не удалось, блок рисует экран диагностики
(`describeData`) с ключами ответа, списком `columns`, первыми строками и
счётчиками разбора — DevTools для этого не нужен. Если пришла только одна
категория без `|~|`, экран сам показывает готовую формулу `gantt_key`.

## Отображение

- **Строки:** группы по `zni_number`; под каждой — исполнители. Клик по строке
  ЗНИ в левой панели сворачивает/разворачивает группу. В свёрнутой группе
  показывается сумма по всем исполнителям за день.
- **Шапка:** селектор квартала `qrt` («Весь период» + значения из данных),
  градиентная легенда часов, кнопки «Развернуть все» / «Свернуть все», статистика.
- **Ось X:** все дни диапазона; «Весь период» — от минимальной до максимальной
  даты данных, квартал — полные границы (`1-е число` … `последний день`).
- **Цвет дня:** глобальная шкала `0 → max(hours)` (5 стопов, отдельные наборы для
  светлой/тёмной темы). Максимум учитывает и агрегаты свёрнутых групп, поэтому
  шкала стабильна между фильтрами.
- **Цвет практик:** `PRACTICE_COLORS` по алфавиту названий практик.
- **Подписи X:** при обзоре всего периода — только месяцы; при зуме ≤ 140 дней
  добавляются числа `5/10/15/20/25`. Месяц подписывается 1-м числом (у января —
  с годом). Это обходит `hideOverlap`, который иначе выбрасывает месяцы.
- **Декор:** полосы групп, зебра исполнителей, выходные (сб+вс объединены),
  вертикальные линии границ месяцев.
- **Вертикальная крутилка справа:** кастомный HTML-элемент поверх canvas
  (`.pg-vbar` / `.pg-vthumb`), высота дорожки = область строк
  (`GRID_TOP`..`GRID_BOTTOM`). Ползунок пропорционален числу видимых строк,
  перетаскивается (`pointerdown` + `setPointerCapture`), клик по треку —
  прыжок к позиции, колесо над полосой — построчный скролл. При нехватке строк
  скрывается. Позиция синхронизирована с `state.yStart` через `applyYWindow()`.

## Взаимодействие

| Действие | Результат |
|----------|-----------|
| Клик по строке ЗНИ в левой панели | Свернуть / развернуть группу |
| Колесо мыши | Вертикальный скролл строк |

| Нижний слайдер | Панорама / зум по времени |
| Hover по ячейке | Тултип: ЗНИ, исполнитель (или «N исполнителей» для агрегата), практика, дата, часы |
| Селектор «Квартал» | Смена диапазона дней |

## Грабли

- **ECharts 5.4.3:** в `renderItem` custom series **не передаётся `params.data`** —
  только `params.dataIndex`. Элементы берутся из `viewCells[dataIndex]` /
  `viewDecor[dataIndex]`, а не из `params.data`.
- `dataZoom`: `filterMode: 'none'`, id `dzX` / `dzY` / `dzXSlider`; вертикальное
  окно строк применяется через `dispatchAction` (`startValue` / `endValue`).
- Левая панель — rich-text в `yAxis.axisLabel` (`inverse: true`, `margin:
  LEFT_W - 16`), а не отдельный HTML; ширина `LEFT_W = 500`.
- Тема адаптивная (`window.themeConfigs`), отслеживание — `MutationObserver` +
  `postMessage({ type: 'THEME_CHANGED' })`.
- **`<style id="pixbi-gantt-style">` перезаписывается при каждом запуске.**
  Дашборд PIX BI — SPA: после повторного рендера визуала старый тег остаётся
  в `<head>`, и если вставлять стили только при его отсутствии, новые классы
  (например, `.pg-vbar`) не применяются. Поэтому `textContent` обновляется
  всегда.
- В шапке справа отображается версия скрипта (`v2.2`) — по ней видно, что
  PIX BI подхватил новую версию, а не закешировал старую.

## Диагностика данных Ганта (`diag_gantt.js`)

Короткий скрипт: вставляется в блок PIX BI **вместо** `gantt.js`. График не
рисует — печатает отчёт прямо в блоке (DevTools не нужен):

1. `BLOCK_ID`, ключи ответа `getItemData`, число строк, первая сырая строка.
2. Разделитель ключа и распределение по числу частей (`5 (1373)`).
3. Счётчики разбора: **принято / без даты / без ЗНИ / без часов**.
4. Уникальные ЗНИ, исполнители, практики, кварталы; число дней, период, сумма
   часов и первые 3 разобранные строки.
5. Сверка с `EXPECTED` — ожидаемыми значениями датасета (1373 строки, 69 ЗНИ,
   21 исполнитель, 2 практики, 3601.55 ч, `2025-01-29 .. 2026-10-16`).
   Расхождения при включённых фильтрах PIX BI — нормальны.
6. **ИТОГ**: «✅ Данные разбираются…» либо конкретная причина (одна категория без
   разделителя → готовая формула `gantt_key`; ни одна строка не разобрана →
   пример проблемной строки).

`EXPECTED` в начале файла обновить при смене датасета. `BLOCK_ID`
переопределяется через `window.__DIAG_GANTT_BLOCK_ID__`; кнопка «Перепроверить» +
автоповтор через 2,5 с. Локально: `debug_gantt.html?format=csvkey&diag=1`.

## Диагностика категорий (`diag_categories.js`)

Отдельный диагностический скрипт: вставляется в блок PIX BI **вместо**
`gantt.js`, когда нужно понять, как платформа отдаёт **несколько отдельных
категорий**. Ничего не рисует — печатает отчёт прямо в блоке (DevTools не нужен).

Что показывает:

1. `typeof getItemData`, её арность и первые 400 символов исходника.
2. Верхний уровень ответа: все ключи, `categories` / `values` / `columns` /
   `rows`, число строк и число уникальных `categories[i].name`.
3. Дерево ответа (первые 3 элемента каждого массива, глубина 6).
4. Все собственные поля объектов категорий (какие ключи встречаются и как часто).
5. Глубокий поиск массивов длиннее 1 внутри ответа — там могли бы прятаться
   колонки с остальными категориями.
6. Проверка способов чтения: `categories[i].name` массив-кортеж, объект-колонка
   `{name, values}`, транспонированные колонки, таблица `values + columns`,
   мера в `series` / `value`.
7. Вызов `getItemData` с другими аргументами: без аргумента, с ID, с DOM-элементом,
   с `{id}` — вдруг полный ответ отдаётся при другой сигнатуре.
8. Хранилище `window.itemsData`: его ключи, значение этого блока и составные
   ключи, содержащие ID блока. `getItemData` — это просто
   `(id) => window.itemsData[id] || {}`.
9. `getDataSets()` / `getDataSets(BLOCK_ID)` / `getDataSets({id})` и другие
   глобальные функции API (`getBlockData`, `getData`, `getCubeData`, …).
10. Соседние хранилища `window.dataSets`, `window.dashboardByIdData`,
    `window.dashboardItems` — их структура и все пути, где упоминается ID блока
    или имя датасета (`findPaths`).
11. `data_configs` блока (`dashboardItems[0].data_configs.categories / values /
    series`) — сколько категорий реально сохранено в дашборде, и описание
    датасета из `dataSets` (какие поля в нём есть).
12. Короткий **ИТОГ** — он дублируется первой строкой отчёта.

Вердикты:

- «категории приходят КОРТЕЖЕМ» — несколько полей читаются напрямую;
- «ОТДЕЛЬНЫМИ КОЛОНКАМИ» / «ТАБЛИЦЕЙ values+columns» — тоже напрямую;
- «платформа отдала ОДНУ категорию» — эта версия `getItemData` передаёт только
  первую категорию, нужен ключ через `|~|` (или `||` — `gantt.js` понимает оба).

**Устройство API (проверено на прод-блоке 19.10.2026):**

```js
getItemData = (id) => window.itemsData[id] || {};
```

- С пустым аргументом, DOM-элементом и `{id}` возвращает `{}` — работает только
  строковый ID блока.
- При 5 настроенных категориях в ответе 69 строк (число уникальных
  `zni_number` — первой категории), а не 1373 комбинации. Платформа группирует
  **только по первой категории**; её порядок в «Категориях» определяет, какое
  поле придёт (`dt` раньше, `zni_number` после смены порядка).
- У объектов категорий есть только `name`, `series`, `extra_hints`;
  `metadata` / `customValues` — `undefined`.
- В `data_configs` блока сохранены **4 категории** (`zni_number`, `full_name`,
  `practice` и ещё одна) — то есть конфигурация полная, но в ответ всё равно
  попадает только первая. Датасет `v_serv_jira_zni_gant` содержит 22 поля —
  сервер их видит, но в `itemsData` отдаёт агрегат по первому.
  Вывод: ограничение на стороне платформы, а не настройки блока.
- `getDataSets` существует (`() => window.dataSets || {}`) и возвращает
  `{ accessModifiers, data }` — там только определения датасетов (`data_sets`
  с полями), строк данных нет. `window.dashboardByIdData` /
  `window.dashboardItems` — конфигурация дашборда и блока, строк данных нет.
- Для даты в `concat` нужен строковый тип: `toString(dt)` (ClickHouse/ADQM),
  иначе `cast(dt as varchar)` или `to_char(dt, 'YYYY-MM-DD')`.

`BLOCK_ID` в начале файла (по умолчанию ID блока Ганта), переопределяется через
`window.__DIAG_BLOCK_ID__`. Кнопка «Перепроверить» и автоповтор через 2,5 с —
данные PIX BI грузятся асинхронно.

# lineage_v2.js (актуальная версия)

## Архитектура: один блок, склейка пути через `||`

v2 использует **один блок PIX BI** с **одним вычисляемым полем** `lineage_key`,
в котором весь путь склеен через разделитель слоёв `||`. Каждый сегмент между
`||` = один слой графа (по позиции). В отличие от v1, число слоёв **динамическое**
(определяется числом сегментов), а не захардкожено.

```
lineage_key (одно поле) ──► lineage_v2.js ──► ECharts Graph
  "Схема::v1::инфо || Таблица::v2::инфо || Витрина::v3::инфо || Дашборд::v4::инфо"
       слой 0            слой 1           слой 2            слой 3
```

### Конфигурация в PIX BI

**Блок** (где `lineage_v2.js`):
- **Категории:** ОДНО вычисляемое поле `lineage_key` (формат ниже)
- **Меры:** `COUNT(1)` — обязательно, иначе 0 строк
- **Серии:** пусто
- `BLOCK_ID` в `lineage_v2.js` = ID этого блока (он же DOM-элемент для рендера)

### Формат данных (`lineage_key`)

Каждая строка `categories[i].name` = одна цепочка пути:

```
Название::значение::инфо || Название::значение::инфо || ...
```

- **Разделитель слоёв:** `||` (`LAYER_SEP`). Каждый сегмент = слой по позиции.
- **Внутри сегмента:** `Название::значение::инфо` (`FIELD_SEP` = `::`).

| Часть | Назначение |
|-------|------------|
| `Название` | Метка слоя (легенда). Слой определяется ПОЗИЦИЕЙ, не названием — одинаковые названия на разных слоях допустимы. |
| `значение` | Имя узла (внутри узла и в тултипе). |
| `инфо` | Доп. информация (синим в тултипе). Может быть пустым. |

Связи строятся **внутри строки**: сегмент i → следующий непустой сегмент i+1.
Отдельный «ключ» не нужен. Пустые сегменты (значение `''`) пропускаются — ребро
идёт к ближайшему непустому слою справа. Завершающий `||` (пустой хвостовой слой)
игнорируется.

**Пример SQL (PIX BI вычисляемое поле):**
```sql
concat(
  'Схема в GreenPlum',  '::', coalesce(table_schema,''), '::', concat('Домен СИДа: ', coalesce(sid_domen,'')), '||',
  'Таблицы в GreenPlum','::', coalesce(table_name,''),   '::', concat('Домен СИДа: ', coalesce(sid_domen,'')), '||',
  'Витрины в GreenPlum','::', coalesce(view_schema,''),  '::', concat('Домен СПДа: ', coalesce(spd_domen,'')), '||',
  'Витрины в GreenPlum','::', coalesce(view_name,''),    '::', concat('Домен СПДа: ', coalesce(spd_domen,''))
) as lineage_key
```

### `BLOCK_ID`

В начале `lineage_v2.js`:

```js
const BLOCK_ID = 'id_блока';   // ID блока, он же DOM-элемент для рендера
```

**Число и порядок слоёв** задаётся числом и порядком сегментов в `lineage_key`
(макс. 20 — по размеру палитры). Чтобы добавить/убрать слой — правится SQL-формула,
код менять не нужно.

## 🏗 Архитектура графа (v2)

### Слои

Один сегмент `||` = один слой = одна колонка на графе.
Слои идут слева направо в порядке сегментов в `lineage_key`.
Метка слоя берётся из поля `Название` первого непустого сегмента на этой позиции.

### Цвета

Назначаются из палитры 20 цветов по индексу слоя:

| Индекс | Цвет |
|--------|------|
| 0 | `#22c55e` зелёный |
| 1 | `#eab308` жёлтый |
| 2 | `#3b82f6` синий |

### Связи (Edge)

- Рёбра строятся ВНУТРИ каждой строки `lineage_key`.

## 🎨 Дизайн и поведение (v2)

### Узлы
- `symbol: 'roundRect'`, фиксированный размер `[NODE_W, NODE_H]`
  (`NODE_W = 160`, `NODE_H = 30`) — узлы НЕ сжимаются
- Цвет — `COLOR_PALETTE[layerIndex]`, обводка `#fff`, подпись внутри
- Слои по горизонтали: динамический зазор `dynGap`, подбирается под ширину блока
  - `MIN_LAYER_GAP = 80` (править вручную, строка с комментарием `← ПРАВИТЬ ЗДЕСЬ`)
  - `COMFORTABLE_GAP = NODE_W + 80 = 240` — когда хватает места
  - Пустые слои (без узлов): `EMPTY_LAYER_GAP = 30` — чтобы соседние непустые слои не разъезжались
  - Если слои не влезают даже с `MIN_LAYER_GAP` → горизонтальный скролл
- Узлы внутри слоя — вертикально, шаг `NODE_H + V_GAP` (`V_GAP = 24`),
  сортировка по имени

### Размер canvas и обход авто-fit (важно)
ECharts с `layout:'none'` по умолчанию **авто-вписывает** (fit) весь граф в
размер контейнера — при множестве узлов это схлопывает их в кучу. Декларативный
`zoom`/`center` это не лечит (fit перебивает их).

Решение: **canvas делается физически равным размеру графа**.
- Узлы сдвигаются в положительные координаты от `(PAD, PAD)` (`PAD = 80`).
- Вычисляются `logicalW × logicalH` по bbox узлов + поля.
- Внутри `scrollEl` (прокручиваемый контейнер) создаётся `innerEl` размером
  `logicalW × logicalH`, и ECharts рендерит **на нём**. Авто-fit становится
  тождественным (вписывать граф в canvas его же размера нечего) → масштаб 1,
  узлы натуральные, зазоры держатся.
- `scrollEl.style.overflow = 'hidden'` — панорамирование/зум только через
  ECharts `roam` (иначе scrollEl перехватывает мышь и ломает draggable).
- После рендера `centerScroll()` ставит середину графа по центру видимой области
  (с повтором — PIX BI грузится асинхронно, `clientWidth/Height` могут быть 0).

### Структура DOM внутри блока
```
el (flex column, overflow:hidden)
├── headerEl (flex-shrink:0) — фиксированная HTML-легенда (не скроллится)
└── scrollEl (flex:1, overflow:hidden) — область с графом (pan/zoom через roam)
    └── innerEl (logicalW × logicalH) — ECharts canvas
```
Легенда вынесена из ECharts в отдельный HTML (цветные квадраты + названия слоёв)
и зафиксирована вверху — больше не уезжает вместе с графом при скролле.

### Рёбра
- Направленные (`edgeSymbol: ['none', 'arrow']`), `curveness: 0.3`
- По умолчанию `#94a3b8`, при выделении пути — `#60a5fa`

### Взаимодействие
- **Hover / клик** → подсветка полного пути: узел увеличивается, предки —
  синяя обводка, потомки — зелёная, рёбра пути жирные/синие, остальное гаснет.
  Клик закрепляет (`lockedNodeId`), повторный клик / клик по пустому месту — снимает.
- **Двойной клик** → сброс.
- **Тултип**: `_fullName`, `_info` (синим), название слоя + индекс, `refCount`.
- `roam` (zoom/pan) + `draggable` (перетаскивание узлов), `scaleLimit` 0.3..4.
- Панорамирование/зум мышью через roam (scrollEl с overflow:hidden,
  нативный скролл не используется). Дефолтный фокус — центр графа (`centerScroll`).
- `currentView()` читает текущий zoom/center из модели ECharts, чтобы подсветка
  пути (`replaceMerge`) не сбрасывала ручной зум/панораму к стартовому виду.
- `getCurrentPositions()` — читает живые x/y узлов из модели ECharts. Подмешивается
  в highlight/reset, чтобы replaceMerge не сбрасывал позиции, изменённые драгом.
- **Перетаскивание узлов**: после драга позиция сохраняется в модели ECharts.
  `buildHighlightedOption` / `buildResetOption` используют `getCurrentPositions()`,
  а не статичный `nodeData`, поэтому драг не сбрасывается при hover/click/reset.

### Тема
- Адаптивная из `window.themeConfigs`.
- Отслеживание: `MutationObserver` + `postMessage` (`THEME_CHANGED`).
- При смене темы перерисовывается и HTML-легенда (цвет текста).

### Диагностика
- Если нет данных — дамп на canvas с подсказками.
